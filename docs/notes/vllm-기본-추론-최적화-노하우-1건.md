### 들어가며

---

SceneMaker 가 **같은 GPU 로 더 많은 요청을, 더 적은 계산으로** 처리하려고 vLLM 서버와 요청하는 쪽에 적용한 설정을 정리한 글이다.

SceneMaker 는 영상을 듣고(받아쓰기·교정·요약·화자 이름), 보고(컷 판정·시퀀스·씬), 질의에 맞춰 장면을 고른다(편성). 이 일에 들어가는 언어 모델·임베딩·받아쓰기 추론은 GPU 서버 한 대의 vLLM 이 맡는다. 화자 분리나 얼굴 인식처럼 vLLM 밖에서 도는 모델은 이 글에서 다루지 않는다.

![image](/img/notes/vllm-기본-추론-최적화-노하우-1건/img-00.jpg)

- GPU 서버에는 96GB GPU 4장이 있고, vLLM 엔진이 다섯 개 올라간다. 언어 모델(Qwen3.8-27B-FP8) 3개, 임베딩(Qwen3-Embedding-4B) 1개, 그리고 받아쓰기 서버 안에 내장된 받아쓰기 엔진(Qwen3-ASR-1.7B) 1개다.
- 요청은 많다. 드라마 10회차에서 컷이 12,540개 나왔고, 컷마다 언어 모델을 한 번씩 부른다. 교정·요약·화자 이름·시퀀스·씬·편성 호출이 그 위에 더해진다.
- 그래서 호출 하나를 빠르게 하는 것보다 **GPU 를 놀리지 않고, GPU 가 할 일을 줄이는 것** 이 중요하다.

이 글에서 다루는 내용은 아래와 같다.

1. 추론에서 시간이 드는 곳
2. 메모리를 아껴 많이 올리기
3. 여러 요청을 묶어 GPU 채우기
4. 같은 계산 다시 하지 않기
5. 만들 토큰 줄이기
6. 호출 수 줄이기

1·2절은 서버 설정을, 3절부터는 서버 설정과 **요청하는 쪽의 설정** 을 함께 본다.

---

#### 1. 추론에서 시간이 드는 곳

언어 모델 추론은 두 단계로 나뉜다.

- **입력 읽기 (Prefill):** 지시문·대사·화면을 한 번에 읽어 KV 캐시에 담는다. 토큰 수천 개를 동시에 계산하므로 **계산량** 이 병목이다.
- **답 쓰기 (Decode):** 토큰을 하나씩 만든다. 토큰 하나를 만들 때마다 모델 가중치와 KV 캐시를 메모리에서 다시 읽으므로 **메모리 읽기** 가 병목이다.

![image](/img/notes/vllm-기본-추론-최적화-노하우-1건/img-01.jpg)

Flash Attention·PagedAttention 같은 커널 수준의 최적화는 vLLM 이 기본으로 쓴다. 이 글은 그 위에서 **설정으로 고를 수 있는 것** 만 다룬다.

---

#### 2. 메모리를 아껴 많이 올리기

**2-1. FP8 가중치**

- 모델 가중치 크기는 파라미터 수에 파라미터 하나의 바이트 수를 곱한 값이다. 27B 모델을 BF16(2바이트)으로 올리면 약 54GB, **FP8(1바이트)이면 약 27GB** 다. FP8 모델도 보통 일부(입력·출력층, 이미지를 읽는 부분 등)는 BF16 으로 남겨 두므로, 실제 가중치는 이보다 몇 GB 크다.
- 줄어든 만큼이 KV 캐시 자리가 된다. KV 캐시가 넓을수록 동시에 진행할 수 있는 요청이 많아진다(3절).

![image](/img/notes/vllm-기본-추론-최적화-노하우-1건/img-02.jpg)

- 양자화는 모델마다 따로 정한다. 받아쓰기 모델은 양자화하지 않고 BF16 그대로 올린다. 코드 주석에 남은 기록에 따르면, 한국어 음성 평가 데이터(FLEURS)에서 8bit 일 때 6.89% 이던 오류율이 4bit 로 줄이자 19.95% 로 올라갔다.

**2-2. 메모리 비율** (`--gpu-memory-utilization` )

- vLLM 은 기동할 때 GPU 메모리 중 이 비율만큼을 잡는다. 가중치를 올리고 계산에 쓸 작업 공간을 잰 뒤, **남은 자리를 전부 KV 캐시로 미리 확보** 한다.
- 언어 모델은 0.85(약 82GB), 임베딩은 0.10(약 10GB)을 준다. 받아쓰기 엔진은 설정 예시 파일 값이 0.4 이고, 비율이 GPU 전체 메모리 기준이라 GPU 가 바뀌면 다시 맞춘다.
- 받아쓰기 엔진의 단어 시각 정렬기는 vLLM 이 아니라 transformers 로 올라가, 비율 밖에서 약 1.2GB 를 더 쓴다. 같은 GPU 를 쓰는 다른 엔진은 그만큼 여유를 남겨야 한다.

**2-3. GPU 1장에 모델 1개** (`--tensor-parallel-size 1` )

- 27B FP8 모델은 GPU 1장(96GB)에 다 들어간다. 그래서 모델을 여러 GPU 에 쪼개지(텐서 병렬) 않는다. 쪼개면 층마다 GPU 끼리 계산 결과를 주고받아야 하는데, 1장에 다 들어가면 그 통신이 없다.
- 대신 **같은 모델을 3개 띄워** 요청을 나눠 받는다(데이터 병렬). 요청하는 쪽이 이 3개를 어떻게 쓰는지는 3절에서 본다.

**2-4. 최대 길이** (`--max-model-len` )

- 언어 모델은 131,072 토큰, 임베딩은 2,048 토큰이다.
- vLLM 은 KV 캐시를 작은 블록 단위로 필요할 때 나눠 준다(PagedAttention). 그래서 최대 길이를 길게 잡아도 짧은 요청은 짧은 만큼만 자리를 쓴다.
- 임베딩은 씬 요약이나 대사 한 줄처럼 짧은 글만 받으므로 작게 둔다.

---

#### 3. 여러 요청을 묶어 GPU 채우기

- 답 쓰기는 토큰 하나마다 가중치를 메모리에서 읽는다. 요청 하나만 진행하면 그 읽기가 토큰 하나를 위해 쓰인다.
- vLLM 은 진행 중인 요청을 **매 스텝 한 묶음으로 함께 계산** 한다(continuous batching). 한 번 읽은 가중치로 여러 요청의 토큰을 동시에 만든다. 끝난 요청이 빠지면 대기 중인 요청이 바로 그 자리에 들어간다.
- 묶음 크기의 상한(`--max-num-seqs` )은 언어 모델 엔진마다 24, 임베딩은 4 다.
- 서버가 묶어 주려면 요청하는 쪽이 **동시에 여러 개를 보내야** 한다. 하나 보내고 답을 기다린 뒤 다음을 보내면 묶음은 늘 하나다. 반대로 한꺼번에 너무 많이 보내면 서버 대기열이 길어지고 응답이 늦어진다. 그래서 세 서비스 모두 **동시 전송 수의 상한을 정해 두고** , 그 안에서는 최대한 동시에 보낸다.

![image](/img/notes/vllm-기본-추론-최적화-노하우-1건/img-03.jpg)

**3-1. 자막 서비스: 서비스 전체에 동시 8**

- 자막 서비스는 언어 모델 주소를 하나 받아, 그 엔진 한 대로 보낸다.
- 동시 상한 8 은 단계별이 아니라 **서비스 전체에 하나** 다. 명단 검색·교정·환각 판정·요약·화자 이름의 모든 호출이 이 상한을 함께 쓴다.
- 1분 단위 요약은 구간들을 **8덩이로 나눠 덩이끼리 동시에** 돌린다. 덩이 안에서는 직전 요약 3개를 문맥으로 넘겨야 해서 순서대로 돈다. 덩이 수를 동시 상한과 같게 맞췄다. 더 쪼개도 상한 앞에서 기다릴 뿐이다.
- 이 구조를 고른 이유가 코드 주석에 측정값과 함께 남아 있다. 구간 115개를 순서대로 요약하면 3분 56초가 걸렸다. 여러 구간을 한 호출에 묶어 8번만 부르면 43초로 줄었지만, 요약 길이가 30% 줄고 빈 요약이 생기고 구간끼리 내용이 섞였다. 그래서 **호출은 그대로 두고 동시에 보내** 서버가 묶게 했다.

**3-2. 화면 분석 · 편성 서비스: 엔진마다 상한, 덜 바쁜 곳으로**

- 두 서비스는 언어 모델 엔진을 **목록** 으로 받는다. 엔진마다 동시 상한을 따로 두고, 요청을 보낼 때마다 **부하율(처리 중 ÷ 동시 상한)이 가장 낮은 엔진** 을 고른다. 상한은 그 엔진의 묶음 상한에 맞추게 되어 있고, 설정 예시 파일의 값은 8 이다.
- 화면 분석 서비스는 엔진마다 이미지를 받는지도 적어 둔다. 이미지가 있는 컷 판정은 이미지를 받는 엔진으로만 보내고, 글자만 있는 요청은 이미지를 받지 않는 엔진을 먼저 쓴다. 이미지를 받는 자리를 아끼기 위해서다.
- 오류가 계속 나는 엔진은 목록에서 빼고 남은 엔진으로 넘긴다.
- 컷 판정은 대상 컷 전부를 한꺼번에 띄우고, 실제로 나가는 수는 이 상한이 조절한다.

#### 4. 같은 계산 다시 하지 않기

- 입력 읽기는 계산이 병목이다. 그런데 SceneMaker 의 요청은 **앞부분이 같은 경우가 많다.** 같은 지시문을 수천 번 보낸다.
- 프리픽스 캐싱(`--enable-prefix-caching` )을 켜면 vLLM 은 입력의 앞부분을 블록 단위로 비교해, 이전에 계산한 블록이면 **저장해 둔 KV 캐시를 그대로 쓰고 계산을 건너뛴다.** 최신 vLLM 엔진에서는 기본으로 켜져 있지만, 실행 설정에 명시해 둔다.
- 재사용은 **맨 앞에서부터 같은 데까지만** 된다. 중간에 한 글자라도 다르면 그 뒤는 다시 계산한다. 그래서 요청하는 쪽은 **변하지 않는 내용을 앞에, 매번 바뀌는 내용을 뒤에** 둔다.

![image](/img/notes/vllm-기본-추론-최적화-노하우-1건/img-04.jpg)

- **교정:** 교정 지시문 뒤에 영상 정보·용어집·등장인물 명단을 붙여 앞에 둔다. 이 넷은 한 회차 안의 모든 페이지가 같다. 페이지마다 바뀌는 대사 30줄은 뒤에 온다.
- **컷 판정:** 판정 규칙 뒤에 회차의 등장인물과 개요를 붙여 앞에 둔다. 한 회차의 모든 컷이 같은 앞부분을 쓴다. 컷마다 바뀌는 시퀀스 맥락·대사·시각·화면은 뒤에 온다.
- **시퀀스 보정 · 씬 묶기:** 단계 지시문과 회차의 등장인물·개요를 공통 앞부분으로 두고, 시퀀스마다 바뀌는 요약·컷·대사를 뒤에 붙인다.

---

#### 5. 만들 토큰 줄이기

답 쓰기는 토큰을 하나씩 만든다. **만들 토큰이 적을수록** 호출이 빨리 끝나고, 그 자리를 다음 요청이 쓴다. 줄이는 방법은 세 가지다.

- **사고(thinking) 끄기:** Qwen3 계열은 답 앞에 사고 과정을 길게 쓴다. 판정·교정처럼 답이 정해진 일에는 필요 없어서, 호출마다 꺼서 보낸다. 화면 분석 서비스는 같은 입력에 같은 답이 나오도록 온도(temperature)도 0 으로 둔다.
- **호출별 답 길이 상한:** 일마다 필요한 길이가 다르다. 한 값으로 묶지 않고 호출마다 정한다. 컷 판정은 설명·장소·유형·인물 네 줄이라 240 토큰으로 둔다. 회차의 모든 컷에 걸리는 값이라, 호출 하나의 상한이 전체 생성량을 정한다.
- **형식 강제는 필요한 곳만:** JSON 형식을 강제하면 토큰마다 형식 검사가 붙는다. 기계가 읽어야 하는 답(검색어 생성, 교정, 환각 판정)에만 쓴다. 명단 추출은 일부러 텍스트로 받는다. 형식 검사 비용이 없고, 결과를 교정 지시문에 그대로 붙일 수 있다.

![image](/img/notes/vllm-기본-추론-최적화-노하우-1건/img-05.jpg)

**5-1. 편성: 사고는 한 호출에만, 시간으로 끊기**

- 편성에서 사고를 켜는 호출은 **씬 고르기 하나** 다. 시퀀스의 후보 씬을 비교해 질의에 맞는 씬을 고르는 일이라 사고가 답의 질을 올린다. 나머지 호출은 모두 끈다. 전체 스위치를 꺼 두면 이 호출도 사고 없이 보낸다.
- 사고를 켜면 사고와 답이 같은 상한을 나눠 쓰므로 상한을 크게(32,768) 잡는다. 대신 **토큰이 아니라 시간으로 끊는다.** 480초 안에 끝나지 않거나 본문이 비어 있으면 요청을 취소하고, 사고를 끈 채 한 번 더 묻는다.
- 시간으로 끊는 이유가 코드 주석에 남아 있다. 멈춘 호출은 수백 초를 쓰고도 빈 답을 냈고, 사고를 끈 재시도는 1초 만에 같은 답을 냈다. 사고가 길어지는 것은 답에 다가가는 과정이 아니라 멈춘 상태였다.
- 요청을 취소하면 vLLM 도 그 요청을 묶음에서 빼고 자리를 돌려준다. 끝나지 않을 사고가 GPU 자리를 계속 붙들지 않는다.
- 사고량은 설정으로 정한다. 설정 예시 파일의 값은 '낮음(low)'이다.

![image](/img/notes/vllm-기본-추론-최적화-노하우-1건/img-06.jpg)

#### 6. 호출 수 줄이기

호출 하나에는 요청 전송, 대기열, 입력 읽기 같은 고정 비용이 붙는다. 같은 일을 **더 적은 호출로** 하면 그 비용이 준다. 다만 3-1의 요약처럼 너무 많이 합치면 답의 질이 떨어진다. 그래서 일마다 **질을 지키는 선에서 한 호출에 싣는 양** 을 정했다.

- **교정은 30줄씩:** 대사를 30줄씩 나눠 한 번에 교정한다. 앞뒤 줄을 함께 보여야 이름·용어를 문맥으로 고칠 수 있어서, 한 줄씩 보내지 않는다. 30줄 묶음끼리는 동시에 보낸다(3절).
- **임베딩은 64건씩:** 색인을 만들 때 글 64건을 호출 하나에 담아 임베딩 엔진으로 보낸다.
- **시퀀스·씬은 시퀀스 단위로:** 씬 나누기와 씬 서술은 컷마다가 아니라 시퀀스마다 한 번씩 부른다. 시퀀스 보정의 구간 잡기는 회차마다 한 번이다.
- **화면은 필요한 만큼만, 경로로:** 컷 판정은 컷마다 화면을 1\~3장만 보낸다. 3초 이하 컷은 전부, 그보다 긴 컷은 시작·중간·끝 3장이다. 이미지는 해상도에 비례해 토큰이 되므로 장수만큼 입력 읽기 비용이 는다. 프레임은 영상에서 뽑을 때 1280×720 으로 줄여 둔다.
- 이미지는 파일 내용이 아니라 **파일 경로** 로 보낸다. 프레임 파일이 GPU 서버 디스크에 이미 있으므로, 이미지를 인코딩해 실어 나르는 시간과 요청 크기가 없다. 서버는 허용한 경로 아래의 파일만 읽게 해 두었다(`--allowed-local-media-path` ).

---

### 마무리

---

SceneMaker 의 vLLM 최적화는 두 갈래다.

- **GPU 를 놀리지 않기:** FP8 로 가중치를 줄여 KV 캐시 자리를 넓히고, 요청하는 쪽이 엔진의 묶음 상한에 맞춰 동시에 보내 서버가 묶어 계산하게 한다.
- **GPU 가 할 일을 줄이기:** 고정 내용을 앞에 두어 입력 계산을 재사용하고, 사고를 끄고 답 길이를 호출마다 정해 생성 토큰을 줄이고, 한 호출에 싣는 양을 정해 호출 수를 줄인다.

서버 설정만으로는 반쪽이다. 묶음 계산과 캐시 재사용은 **요청하는 쪽이 동시에 보내고, 같은 앞부분을 유지할 때** 효과가 난다.
