### 들어가며

---

SceneMaker 가 **같은 GPU 로 더 많은 요청을, 더 적은 계산으로** 처리하려고 vLLM 서버와 요청 코드에 적용한 설정을 정리한 글이다.

<!--truncate-->

SceneMaker 는 영상을 듣고(받아쓰기·교정·요약), 보고(컷 판정·씬 묶기), 질의에 맞춰 장면을 고른다(편성). 이 세 일에 들어가는 언어 모델·임베딩·받아쓰기 추론은 GPU 서버 한 대의 vLLM 이 맡는다. 화자 분리(pyannote)처럼 vLLM 밖에서 도는 모델은 이 글에서 다루지 않는다.

![image](/img/blog/vllm-기본-추론-최적화-노하우-1건/img-00.png)

- GPU 서버에는 vLLM 엔진이 **5개** 떠 있다.

| 엔진 | 모델 | 띄우는 방식 | 맡는 일 |
| --- | --- | --- | --- |
| 언어 모델 × 3 | `Qwen3.8-27B-FP8` | `vllm serve` (:8601 · :8602 · :8603) | 교정 · 요약 · 화자 이름 · 컷 판정 · 씬 묶기 · 편성 |
| 임베딩 × 1 | `Qwen3-Embedding-4B` | `vllm serve` (:8500) | 씬 색인 · 질의 검색 |
| 받아쓰기 × 1 | `Qwen3-ASR-1.7B` | 작업 서버 안에 내장 (`LLM()` ) | 1차 전사 |

- 요청은 많다. 드라마 「김부장」 10편에서 컷이 **12,540개** 나왔고, 컷마다 언어 모델을 한 번씩 부른다. 교정·요약·편성 호출이 그 위에 더해진다.
- 그래서 한 번의 호출을 빠르게 하는 것보다 **GPU 를 놀리지 않고, GPU 가 할 일을 줄이는 것** 이 중요하다.

이 글에서 다루는 내용은 아래와 같다.

1. 추론에서 시간이 드는 곳
2. 메모리를 아껴 많이 올리기
3. 여러 요청을 묶어 GPU 채우기
4. 같은 계산 다시 하지 않기
5. 만들 토큰 줄이기
6. 호출 수 줄이기


1·2절은 서버(`vllm serve` 옵션), 3절부터 6절까지는 서버 옵션과 **요청하는 쪽(agent) 코드 설정** 을 함께 본다.

---

##### 1. 추론에서 시간이 드는 곳

- 언어 모델 추론은 두 단계로 나뉜다.
  - **입력 읽기 (Prefill)** — 지시문·대사·프레임을 한 번에 읽어 KV 캐시에 담는다. 토큰 수천 개를 동시에 계산하므로 **계산량** 이 병목이다.

  - **답 쓰기 (Decode)** — 토큰을 한 개씩 만든다. 토큰 하나를 만들 때마다 모델 가중치와 KV 캐시를 메모리에서 다시 읽으므로 **메모리 읽기** 가 병목이다.

![image](/img/blog/vllm-기본-추론-최적화-노하우-1건/img-01.png)

- 이 글의 최적화는 이 두 병목에 하나씩 대응한다.

| 병목 | 대응 | 절 |
| --- | --- | --- |
| 메모리 크기 | 가중치를 작게, KV 캐시 자리를 넓게 | 2 |
| 답 쓰기의 메모리 읽기 | 한 번 읽을 때 여러 요청을 함께 진행 | 3 |
| 입력 읽기의 계산량 | 앞부분이 같은 입력은 저장해 둔 KV 캐시 재사용 | 4 |
| 답 쓰기 횟수 | 만들 토큰 수 자체를 줄임 | 5 |
| 요청 자체 | 한 번 호출에 여러 건을 싣고, 필요한 입력만 보냄 | 6 |

- Flash Attention·PagedAttention 같은 커널 수준 최적화는 vLLM 이 기본으로 쓴다. 이 글은 그 위에서 **설정으로 고를 수 있는 것** 만 다룬다.

---

##### 2. 메모리를 아껴 많이 올리기

- GPU 는 `RTX PRO 6000` (96GB) 4장이다. 여기에 엔진 5개를 나눠 올린다.

![image](/img/blog/vllm-기본-추론-최적화-노하우-1건/img-02.png)

- 언어 모델 3개는 각각 GPU 1장의 85% 를 쓰므로 GPU 0, 1, 2 에 하나씩 올라간다.
- 임베딩 엔진과 받아쓰기 엔진은 남은 GPU 3 에 있는 것으로 보지만, 실제 배치는 아직 확인하지 못했다(7절). 받아쓰기 엔진이 있는 GPU 에는 같은 작업 서버의 화자 분리 모델도 함께 올라간다.

**2-1. FP8 가중치**

- 모델 가중치 크기는 `파라미터 수 × 파라미터 하나의 바이트 수` 다.
  - 27B 모델을 BF16(2바이트)으로 올리면 약 54GB, **FP8(1바이트)이면 약 27GB** 다.

  - FP8 모델도 보통 일부(입력·출력층, 이미지를 읽는 부분 등)는 BF16 으로 남겨 두므로, 실제 가중치는 이보다 몇 GB 크다.

- 줄어든 만큼이 KV 캐시 자리가 된다. KV 캐시가 넓을수록 동시에 진행할 수 있는 요청이 많아진다(3절).

![image](/img/blog/vllm-기본-추론-최적화-노하우-1건/img-03.png)

- 위 크기는 옵션 값과 모델 크기로 어림한 것이다. 실제 가중치·KV 캐시 크기는 vLLM 기동 로그에 찍히는 값으로 확인한다(7절).
- 양자화는 모델마다 따로 정한다. 받아쓰기 모델은 양자화하지 않고 BF16 그대로 올린다. 4bit 로 줄였을 때 한국어 인식 결과가 크게 나빠진 기록이 코드 주석에 남아 있다.

```python
# worker-prep_stt/lib/model/qwen_asr.py
dtype="bfloat16",  # ⚠ 4bit 양자화 금지 — 한국어가 무너짐 (FLEURS 19.95%@4bit vs 6.89%@8bit)
gpu_memory_utilization=GPU_MEMORY_UTILIZATION,
```

**2-2. 메모리 비율 (** `--gpu-memory-utilization` **)**

- vLLM 은 기동할 때 GPU 메모리 중 이 비율만큼을 잡는다. 가중치를 올리고 계산에 쓸 작업 공간을 잰 뒤, **남은 자리를 전부 KV 캐시로 미리 확보** 한다.
- 엔진마다 비율을 다르게 준다.

| 엔진 | 비율 | 약 |
| --- | --- | --- |
| 언어 모델 | 0.85 | 82GB |
| 임베딩 | 0.10 | 10GB |
| 받아쓰기 | 0.4 (설정 예시 파일 값) | 38GB (+ 정렬기 약 1.2GB 별도) |

- 받아쓰기 엔진의 비율은 설정 예시 파일의 값이다. 비율은 GPU 전체 메모리 대비라 GPU 가 바뀌면 다시 맞춘다. 코드 주석에는 실제 사용량이 10GB 미만이라고 적혀 있다.
- 받아쓰기 엔진의 타임스탬프 정렬기는 vLLM 이 아니라 transformers 로 올라간다. 비율 밖에서 메모리를 더 쓰므로 같은 GPU 의 다른 엔진은 그만큼 여유를 남겨야 한다.

```python
# worker-prep_stt/lib/model/qwen_asr.py (docstring 발췌)
# 정렬기는 ... transformers 로 뜬다 → gpu_memory_utilization 바깥에 별도로 ~1.2GB
```

```bash
# worker-prep_stt/.env.example
VLLM_GPU_MEMORY_UTILIZATION=0.4   # ⚠ 총 VRAM 대비 비율 (절대량 아님) — GPU 바뀌면 재조정
```

**2-3. GPU 1장에 모델 1개 (** `--tensor-parallel-size 1` **)**

- 27B FP8 모델은 GPU 1장(96GB)에 다 들어간다. 그래서 모델을 여러 GPU 에 쪼개지(텐서 병렬) 않는다.
  - 쪼개면 층마다 GPU 끼리 계산 결과를 주고받아야 한다. 1장에 다 들어가면 그 통신이 없다.

- 대신 **같은 모델을 3개 띄워** 요청을 나눠 받는다(데이터 병렬). 3절에서 요청하는 쪽이 이 3대를 어떻게 쓰는지 본다.

**2-4. 최대 길이 (** `--max-model-len` **)**

- 언어 모델은 131072 토큰, 임베딩은 2048 토큰이다.
- vLLM 은 KV 캐시를 작은 블록 단위로 필요할 때 나눠 준다(PagedAttention). 그래서 최대 길이를 길게 잡아도 **짧은 요청은 짧은 만큼만** 자리를 쓴다.
- 임베딩은 씬 설명·대사 한 줄처럼 짧은 글만 받으므로 2048 로 작게 둔다.

##### 3. 여러 요청을 묶어 GPU 채우기

- 답 쓰기는 토큰 하나마다 가중치를 메모리에서 읽는다. 요청 1개만 진행하면 그 읽기가 토큰 1개를 위해 쓰인다.
- vLLM 은 진행 중인 요청을 **매 스텝 한 묶음으로 함께 계산** 한다(continuous batching). 한 번 읽은 가중치로 여러 요청의 토큰을 동시에 만든다. 끝난 요청이 빠지면 대기 중인 요청이 바로 그 자리에 들어간다.
- 묶음 크기의 상한이 `--max-num-seqs` 다. 언어 모델은 엔진당 **24** , 임베딩은 **4** 다.
- 언어 모델 엔진 하나는 GPU 1장이다. 엔진마다 있는 24자리는 그 엔진에 요청을 보내는 agent 들이 나눠 쓴다.
- agent-stt·agent-compose 는 vLLM 주소를 하나만 받아 **엔진 1대로만** 보낸다. 여러 엔진에 나눠 보내는 것은 주소 목록을 받는 **agent-vision 뿐** 이다. 운영에서 각 agent 가 어느 포트를 쓰는지는 아직 확인하지 못했다(7절).

![image](/img/blog/vllm-기본-추론-최적화-노하우-1건/img-04.png)

- 서버가 묶어 주려면 요청하는 쪽이 **동시에 여러 개를 보내야** 한다. 하나 보내고 답을 기다린 뒤 다음을 보내면 묶음은 늘 1개다.
- 반대로 한꺼번에 너무 많이 보내면 서버 대기열이 길어지고 응답 시간이 늘어난다.
- 그래서 세 agent 모두 **세마포어로 동시 전송 수를 정해 두고** , 그 안에서는 최대한 동시에 보낸다.

**3-1. agent-stt — 언어 모델 호출 동시 8, 요약은 8덩이 병렬**

- 동시 8 은 받아쓰기(음성 → 글) 개수가 아니다. agent-stt 가 언어 모델에 보내는 호출(명단 검색·교정·환각 판정·요약) 기준이다. 받아쓰기는 worker-prep_stt 안의 엔진이 따로 한다.
- 이 8 은 단계별이 아니라 **agent-stt 전체에 하나** 다. 모든 언어 모델 호출이 세마포어 하나를 함께 쓰고, 영상 여러 편을 함께 처리해도 합쳐서 8 이다.
- 요약은 대사를 1분 구간으로 자르고, 구간들을 **8덩이로 나눠 덩이끼리 동시에** 돌린다.
  - 덩이 안에서는 순서대로 요약한다. 앞 구간 요약 3개를 문맥으로 넘겨야 하기 때문이다.

  - 덩이 수를 동시 상한(8)과 같게 맞췄다. 더 쪼개도 세마포어 앞에서 기다릴 뿐이다.

![image](/img/blog/vllm-기본-추론-최적화-노하우-1건/img-05.png)

```python
# agent-stt/config.py
# ── vLLM 동시성 — 클라이언트 전역 세마포어 (교정·검색 등 모든 vllm 호출이 공유)
VLLM_CONCURRENCY = 8          # 동시 vLLM 호출 상한 (lib/client/vllm.py 가 사용)
# ── 요약 (⑤ summary) — 구간(청크 병렬, 직전 N개 문맥) + 전체(마지막 1콜)
SUMMARY_WINDOW_SEC = 60      # 구간 요약 윈도우(초). 300=5분, 60=1분
SUMMARY_PREV_N = 3           # 구간 요약 시 참고할 직전 구간요약 개수 (앞 흐름 문맥. 뒤는 안 봄)
SUMMARY_CHUNKS = 8           # 구간요약을 몇 덩이로 나눠 동시에 돌릴지. 덩이 안은 순차(문맥 유지),
                             # 덩이끼리는 병렬. VLLM_CONCURRENCY 와 맞추는 게 최적(더 키워도 대기)
```

```python
# agent-stt/lib/client/vllm.py — 주소 1개, 세마포어 1개를 프로세스 전체가 공유
def build() -> VLLMClient:
    """config 로 VLLMClient 1개 생성. main / lifespan 에서 1회 호출해 공유한다."""
    # vLLM 은 인증 없음. SDK 가 빈 키를 거부해서 더미값만 넣는다.
    openai = AsyncOpenAI(base_url=config.VLLM_BASE_URL, api_key="-")
    sem = asyncio.Semaphore(config.VLLM_CONCURRENCY)
```

- 이 구조를 고른 이유가 코드에 측정값과 함께 남아 있다.

```python
# agent-stt/lib/svc/audio/summary/pipe_summary.py (docstring 발췌)
# 왜 이 구조인가 (v1 실측):
#   - 순차 115콜 = 3분56초. 콜당 2초인데 줄줄이 기다리는 게 전부라 대기가 곧 비용.
#   - 여러 구간을 한 프롬프트에 묶어 8콜로 던지면 43초로 줄지만 품질이 깨진다 —
#     요약 길이 −30%, 빈 요약 6개, 구간 간 내용 오염
#   - 청크 병렬은 콜 하나하나가 순차 때와 동일(=품질 동일)한 채로 8줄기가 동시에 흐른다.
```

- 호출을 하나로 합치면 빨라도 답의 질이 떨어진다. 그래서 **호출은 그대로 두고 동시에 보내** 서버가 묶게 한다.

**3-2. agent-vision — 엔드포인트마다 동시 상한, 덜 바쁜 곳으로**

- agent-vision 은 언어 모델 주소를 **목록** 으로 받는다. 주소마다 동시 상한을 따로 두고, 요청을 보낼 때마다 **부하율(처리 중 ÷ 동시 상한)이 가장 낮은 곳** 을 고른다.
- 엔드포인트마다 이미지를 받는지(`vision` )를 적어 둔다. 컷 판정처럼 이미지가 있는 요청은 이미지를 받는 엔드포인트로만 보내고, 글자만 있는 요청은 이미지를 받지 않는 엔드포인트를 먼저 쓰게 되어 있다.
  - 이 규칙은 이미지를 못 받는 엔진이 섞여 있을 때 의미가 있다. 언어 모델 3대는 모두 이미지를 받도록 띄웠으므로, 목록에 모두 이미지 가능으로 적혀 있다면 부하율만으로 나뉜다. 운영 목록의 실제 값은 확인하지 못했다.

- 컷 판정은 대상 컷 전부를 한꺼번에 띄우고, 실제로 나가는 수는 이 풀이 조절한다.
- 동시 상한은 엔드포인트마다 설정으로 준다. 설정 예시 파일의 값은 8 이다.

![image](/img/blog/vllm-기본-추론-최적화-노하우-1건/img-06.png)

```python
# agent-vision/src/config.py (VllmEndpoint docstring 발췌)
# concurrency 는 해당 서버의 max-num-seqs 와 정합시킨다 (풀이 엔드포인트별 세마포어로 강제
# — 서버 과적재로 인한 지연 폭주 방지)
```

```bash
# agent-vision/.env.example
VLLM_ENDPOINTS=[{"name":"{name}","url":"http://{host}:{port}","model":"{model}","concurrency":8,"vision":true}]
```


##### 4. 같은 계산 다시 하지 않기

- 입력 읽기는 계산이 병목이다. 그런데 SceneMaker 의 요청은 **앞부분이 같은 경우가 많다.** 같은 지시문을 수천 번 보낸다.
- `--enable-prefix-caching` 을 켜면 vLLM 은 입력의 앞부분을 블록 단위로 비교해, 이전에 계산한 블록이면 **저장해 둔 KV 캐시를 그대로 쓰고 계산을 건너뛴다.** 프롬프트는 매번 보내지만 매번 계산하지는 않는다.
  - vLLM V1 엔진에서는 기본으로 켜져 있지만, 운영 명령에 명시해 둔다.

![image](/img/blog/vllm-기본-추론-최적화-노하우-1건/img-07.png)

- 재사용은 **맨 앞에서부터 같은 데까지만** 된다. 중간에 한 글자라도 다르면 그 뒤는 다시 계산한다.
- 그래서 요청하는 쪽은 **변하지 않는 내용을 앞에, 매번 바뀌는 내용을 뒤에** 둔다.

![image](/img/blog/vllm-기본-추론-최적화-노하우-1건/img-08.png)

초록색이 재사용되는 앞부분이다.

##### 5. 만들 토큰 줄이기

- 답 쓰기는 토큰을 한 개씩 만든다. **만들 토큰이 적을수록** 호출이 빨리 끝나고, 그 자리를 다음 요청이 쓴다.
- 줄이는 방법은 세 가지다.
  - **사고(thinking) 끄기** — Qwen3 계열은 답 앞에 사고 과정을 길게 쓴다. 판정·교정처럼 답이 정해진 일에는 필요 없다.

  - **호출별 답 길이 상한** — 일마다 필요한 길이가 다르다. 한 값으로 묶지 않고 호출마다 정한다.

  - **형식 강제는 필요한 곳만** — JSON 형식을 강제하면(guided decoding) 토큰마다 형식 검사가 붙는다. 기계가 읽어야 하는 답에만 쓴다.

| agent | 호출 | 사고 | 답 길이 상한 | 형식 |
| --- | --- | --- | --- | --- |
| agent-stt | 명단 검색 질의 생성 | 끔 | 지정 안 함 | JSON |
|  | 명단 추출 | 끔 | 8192 | 텍스트 |
|  | 교정 (30줄) | 끔 | 지정 안 함 | JSON |
|  | 환각 판정 | 끔 | 4096 | JSON |
|  | 1분 구간 요약 | 끔 | 512 | 텍스트 |
|  | 전체 요약 | 끔 | 2048 | 텍스트 |
| agent-vision | 컷 판정 | 끔 | 120 | 텍스트 2줄 |
| agent-compose | 질의 해석 · 시작·끝점 등 | 끔 | 512 | — |
|  | 선곡 | **켬** | 32768 | — |

**5-3. agent-compose — 선곡만 사고 켬, 시간으로 끊기**

- 편성에서 사고를 켜는 호출은 **선곡 하나** 다. 여러 후보 씬 중 무엇을 쓸지 비교해 고르는 일이라 사고가 답의 질을 올린다. 나머지 호출은 끈다.
- 사고를 켜면 사고와 답이 같은 상한을 나눠 쓰므로 상한을 크게(32768) 잡는다. 대신 **토큰이 아니라 시간으로 끊는다.** 480초 안에 끝나지 않으면 요청을 취소하고, 사고를 끈 채 한 번 더 묻는다.

![image](/img/blog/vllm-기본-추론-최적화-노하우-1건/img-11.png)

```python
# agent-compose/src/infer/chat.py
# 응답 상한 — thinking 은 사고+본문을 같이 소모하므로 크게
MAX_TOKENS = 512
MAX_TOKENS_THINK = 32768
# thinking 시간 가드 — 토큰 상한이 아니라 시간으로 끊는다 (실측: 교착 콜은 수백 초를
# 쓰고도 빈 응답을 냈고, thinking 끈 재시도가 1초 만에 같은 답을 냈다 —
# 폭주는 답에 다가가는 과정이 아니라 교착이다). 걸리면 thinking 을 끄고 1회 재시도한다.
# ⚠ 전송 타임아웃(Settings.llm_timeout)은 이 값보다 커야 한다 — 같거나 작으면 가드가
# 울기 전에 httpx 가 끊는다 (__init__ 이 경고로 드러낸다).
THINK_TIMEOUT_SEC = 480.0
```

- 요청을 취소하면 vLLM 도 그 시퀀스를 묶음에서 빼고 자리를 돌려준다. 끝나지 않을 사고가 GPU 자리를 계속 붙들지 않는다.

```python
# agent-compose/src/infer/chat.py
except (TimeoutError, httpx.TimeoutException) as e:
    ...
    # thinking 교착 — 취소하면 vLLM 도 그 시퀀스를 접어 GPU 를 놓는다
    return await self.chat(system, user, thinking=False, ...)
```

- 사고량은 `reasoning_effort` 로 정한다. 값이 설정돼 있으면 사고를 켜는 호출에 함께 보낸다. 설정 예시 파일의 값은 `low` 다.

```bash
# agent-compose/.env.example

```

- 공개된 agent-compose 코드의 편성 그래프는 야구용이다. 드라마 편성은 같은 구성의 별도 실행본이 돌고 있고, 위 설정은 공통 호출 모듈(`chat.py` ) 기준이다.

### 마무리

---

- SceneMaker 의 vLLM 최적화는 두 갈래다.
  - **GPU 를 놀리지 않기** — FP8 로 가중치를 줄여 KV 캐시 자리를 넓히고, 요청하는 쪽이 서버 상한에 맞춰 동시에 보내 서버가 묶어 계산하게 한다.

  - **GPU 가 할 일을 줄이기** — 고정 지시문을 앞에 두어 입력 계산을 재사용하고, 사고를 끄고 답 길이를 호출마다 정해 생성 토큰을 줄이고, 한 호출에 싣는 양을 정해 호출 수를 줄인다.

- 서버 옵션만으로는 반쪽이다. 묶음 계산과 캐시 재사용은 **요청하는 쪽이 동시에 보내고, 같은 앞부분을 유지할 때** 효과가 난다.

| `--served-model-name` | qwen / qwen-embed | 요청에 쓰는 모델 이름 | — |  |
