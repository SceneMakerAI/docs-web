### 들어가며

---

SceneMaker가 방송 영상을 분석해 저장하는 데이터 구조를 공개한다.

<!--truncate-->

:::note
💡 SceneMaker 는 야구 중계를 반이닝 구간 단위로 받아 분석하고, 하이라이트로 쓸 장면의 **시간좌표** 를 돌려준다.

이 글은 그 과정에서 쌓이는 데이터 구조를 공개한다. 관계형 테이블 18개(MariaDB)와 벡터 컬렉션 1개(Milvus)다.
:::

  
DDL · 컬렉션 정의 · 빈 환경 구축 스크립트 → [https://github.com/SceneMakerAI/sm_db](https://github.com/SceneMakerAI/sm_db)

### 1. 구조

그림 1. 테이블 지도 — 음성·전광판·화면이 합쳐져 편성으로 나간다

![image](/img/blog/09-db-스키마-공개-김부장꺼로-변경할-수도/img-00.png)

음성과 화면을 따로 분석하고, 초 단위로 합친 뒤(`t_play` ), 사건 단위로 묶어(`t_scene` ) 편성(`t_compose` )으로 내보낸다. MariaDB 가 원본이고, Milvus 는 검색을 위한 파생본이다.

| 층 | 테이블 | 무엇 |
| --- | --- | --- |
| 경기 · 구간 | `t_video` · `t_video_file` | 경기 1건 / 반이닝 구간 파일과 처리 상태 |
| 음성 | `t_dialogue` · `t_dialogue_summary` | 해설 대사(화자 · 시각) / 1분 요약 |
| 전광판 검출 | `t_frame_baseball` · `_board` · `_board_detail` · `t_video_board_baseball` | 초마다 전광판을 찾고 항목(이닝 · 카운트 · 아웃 · 주자)을 읽는다 |
| 전광판 상태 | `t_scoreboard_baseball` | 상태가 바뀐 초만 남긴 원장 |
| 화면 | `t_vision` | 컷 단위 샷 유형과 VLM 캡션 |
| 합본 · 구간 | `t_play_baseball` · `t_scene_baseball` | 전광판 ∪ 화면 초 단위 합본 → 사건 단위 플레이 구간 |
| 편성 | `t_compose` · `t_compose_clip` | 질의 1건 → 내보낸 클립 목록 |
| 사전 · 코드 | `t_code` · `t_category` · `t_team_baseball` | 처리 상태(`1000` 업로드 → `20xx` 음성 → `30xx` 화면 → `40xx` 편성, 실패 `x9xx` ) / 분류 / 팀명 별칭 |

`t_chapter` 는 야구 외 장르용 씬 · 막 요약 테이블이다.

### 2. 설계 원칙 셋

**① 키는 두 단계다.** 영상이 한 번에 오지 않고 반이닝 구간씩 실시간으로 들어온다. 그래서 경기 `v_id` 아래 구간 `stream_id` 를 두고, 결과 테이블의 키는 전부 `(v_id, stream_id, …)` 로 시작한다. 구간 단위로 지우고 다시 쌓는 일이 잦아 야구 테이블에는 FK 를 걸지 않았다.

**② 시간축은 둘이고, 정본은 구간 기준이다.** 앞 구간이 재전송되면 그 뒤 구간까지 지우고 다시 쌓는다. 전체 기준 초는 앞 구간 길이의 합이라 이때 전부 밀린다.

그림 2. 1회말이 재전송되면 2회초의 전체 기준 초가 밀린다

![image](/img/blog/09-db-스키마-공개-김부장꺼로-변경할-수도/img-01.png)

매칭과 클립 절단은 항상 `(stream_id, *_stream_sec)` 로 하고, 전체 기준 값은 화면 표시에만 쓴다.

**③ 층마다 근거를 남긴다.** 위 층이 틀렸을 때 아래 층으로 내려가 원인을 찾을 수 있어야 한다.

| 무엇 | 예 |
| --- | --- |
| `NULL` 은 0 이 아니라 “못 읽음” | `ball NULL` = 볼카운트 미인식. 판단 단계는 둘을 구분한다 |
| 품질도 컬럼으로 남긴다 | `check_yn` 검수 제외 · `jumping_cnt` 못 본 투구 수 |
| 아래 층 값을 위 층에 사본으로 둔다 | `tags` · `labels` 를 `t_compose_clip` · Milvus 에 복사 — 조인 없이 거르기 위해 |

### 3. 벡터 저장소

그림 3. 증거는 가장 많이 겹치는 플레이 구간 하나에 매달린다

![image](/img/blog/09-db-스키마-공개-김부장꺼로-변경할-수도/img-02.png)

한 행은 **증거 1건** — 해설 한 마디(`stt` ), 샷 캡션 하나(`shot` ), 하단 자막 하나(`etc` )다. 

증거는 가장 많이 겹치는 플레이 구간 하나에 매달리고, 어디에도 안 걸리면 `-1` 로 남는다.

| 필드 | 쓰임 |
| --- | --- |
| `text` → `vector` | 임베딩 원문과 벡터 (Qwen3-Embedding-4B, 2560차원, COSINE) |
| `v_id` · `stream_id` · `scene_stream_seq` | RDB `t_scene_baseball` 로 돌아가는 키 |
| `inning` · `home_team` · `away_team` · `score` · `labels` · `board_tags` | 구간 속성의 사본 (원칙 ③) |
| `start_sec` · `end_sec` | 구간 기준 초, 소수점까지 |

검색은 필터로 좁히고 벡터로 순위를 매긴다. 예: `v_id == 1044 and inning == "4회말"` 안에서 “삼진” 에 가까운 증거.
