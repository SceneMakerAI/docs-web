### Introduction

---

SceneMaker is releasing the data structures it uses to analyze and store broadcast footage.:

<!--truncate-->

::note
💡 SceneMaker processes baseball broadcasts in half-inning segments, analyzes them, and returns the **timestamps** of scenes suitable for use as highlights.

This article details the data structures accumulated during that process: 18 relational tables (MariaDB) and 1 vector collection (Milvus).
:::

  
DDL · Collection Definitions · Script for Setting Up an Empty Environment → [https://github.com/SceneMakerAI/sm_db](https://github.com/SceneMakerAI/sm_db)

### 1. Structure

Figure 1. Table Map — Audio, LED displays, and video feeds are combined and output as a broadcast

![image](/img/blog/09-db-스키마-공개-김부장꺼로-변경할-수도/img-00.png)

Audio and video feeds are analyzed separately, combined at the second level (`t_play`), grouped by event (`t_scene`), and output as a broadcast (`t_compose`). MariaDB is the source database, and Milvus is a derivative version designed for search.

| Layer | Table | Description |
| --- | --- | --- |
| Game · Segment | `t_video` · `t_video_file` | 1 game / half-inning segment files and processing status |
| Audio | `t_dialogue` · `t_dialogue_summary` | Commentary dialogue (speaker · time) / 1-minute summary |
| Scoreboard Detection | `t_frame_baseball` · `_board` · `_board_detail` · `t_video_board_baseball` | Locates the scoreboard every second and reads the items (inning · count · outs · runners) |
| Scoreboard Status | `t_scoreboard_baseball` | Log retaining only the seconds when the status changed |
| Screen | `t_vision` | Shot type and VLM captions by cut |
| Compilation · Segment | `t_play_baseball` · `t_scene_baseball` | Second-by-second compilation of scoreboard and screen data → Play segments organized by event |
| Schedule | `t_compose` · `t_compose_clip` | 1 query → List of exported clips |
| Dictionary · Code | `t_code` · `t_category` · `t_team_baseball` | Processing Status (`1000` Upload → `20xx` Audio → `30xx` Video → `40xx` Scheduling, Failure `x9xx` ) / Category / Team Name/Alias |

`t_chapter` is a scene and inning summary table for genres other than baseball.

### 2. Three Design Principles

**① The key has two levels.** Video data does not arrive all at once but comes in real time in half-inning segments. Therefore, segments `stream_id` are defined under the game `v_id`, and all keys in the results table begin with `(v_id, stream_id, …)`. Since segments are frequently deleted and rebuilt, foreign keys (FK) were not applied to the baseball tables.

**② There are two time axes, and the master version is based on segments.** If a previous segment is retransmitted, the segments that follow are also deleted and rebuilt. Since the total reference seconds are the sum of the lengths of the preceding segments, they are all shifted at this point.

Figure 2. If the bottom of the 1st inning is retransmitted, the overall reference time for the top of the 2nd inning is shifted

![image](/img/blog/09-db-스키마-공개-김부장꺼로-변경할-수도/img-01.png)

Matching and clip trimming are always performed using `(stream_id, *_stream_sec)`, and the overall reference values are used only for screen display.

**③ Document the rationale for each layer.** If an upper layer is incorrect, it must be possible to trace down to the lower layers to find the cause.

| What | Example |
| --- | --- |
| `NULL` is not 0 but “Unread” | `ball NULL` = Unrecognized pitch count. The decision stage distinguishes between the two |
| Record quality as a column | `check_yn` Excluded from review · `jumping_cnt` Number of pitches not seen |
| Store values from the lower layer as copies in the upper layer | Copy `tags` and `labels` to `t_compose_clip` and Milvus — to filter without a join |

### 3. Vector Storage

Figure 3. Evidence is tied to a single play segment with the most overlap

![image](/img/blog/09-db-스키마-공개-김부장꺼로-변경할-수도/img-02.png)

One row represents **one piece of evidence** — a brief commentary (`stt`), one shot caption (`shot`), and one bottom caption (`etc`). 

Evidence is attached to the play segment with the most overlap; if it doesn’t match any segment, it remains as `-1`.

| Field | Purpose |
| --- | --- |
| `text` → `vector` | Original text and vector (Qwen3-Embedding-4B, 2560-dimensional, COSINE) |
| `v_id` · `stream_id` · `scene_stream_seq` | Keys mapping back to the RDB `t_scene_baseball` |
| `inning` · `home_team` · `away_team` · `score` · `labels` · `board_tags` | Copies of interval attributes (Principle ③) |
| `start_sec` · `end_sec` | Interval-based seconds, including decimals |

Searches are narrowed down by filters and ranked by vectors. Example: Evidence close to “strikeout” within `v_id == 1044 and inning == "4회말"`.
